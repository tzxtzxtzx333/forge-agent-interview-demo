# Forge Agent 面试背诵稿

## 一、30 秒项目介绍

Forge Agent 是一个面向代码仓库工作流的终端式 AI Coding Agent 工程化 MVP。这个项目的重点不是让模型生成一段代码，而是让它在真实仓库里完成一段连续任务，比如读代码、调用工具、运行测试、根据失败结果继续修复，并把整个过程记录成可复盘的 JSONL 执行轨迹。我主要做的是把 ReAct-style 主循环、工具系统、多 Provider 路由、repo-map 上下文摘要、event log、Shell guardrails 和 Docker demo runtime 串成一条完整工程链路，并用测试把这些能力验证下来。

## 二、2 分钟项目讲解

如果用两分钟讲这个项目，我会先从问题出发。大语言模型已经能生成代码，但自主完成编程任务不是一次性输出答案，而是一个持续决策过程。模型需要先观察仓库环境，再决定读什么文件、调什么工具、要不要跑测试、失败后怎么恢复。这背后真正难的是工程闭环，而不是单次生成。

Forge Agent 的目标，就是把这条闭环跑通。我把项目拆成几个层次：入口层接收任务，支持 `run`、`chat` 和 GitHub Issue 驱动三种使用方式；Agent Core 负责 ReAct-style 主循环；LLM 层通过 Router 解耦不同模型厂商；工具层提供文件读写、Shell、Pytest、Git、搜索和符号查找；上下文层通过 history、token budget 和 repo-map 控制上下文；日志层把执行过程写成 JSONL event log，并支持 replay。

这个项目里我认为比较有价值的点有三个。第一，Agent 不是只会“回答”，而是真的能结合 observation 持续迭代。第二，我把模型调用、工具执行、Runtime 边界和日志复盘分层设计，让系统更容易验证和讲清楚。第三，项目没有夸大成更强的安全系统，而是明确保留 Shell guardrails 和 Docker demo runtime 这样的真实边界，所以它既能演示，也能说明工程判断。

## 三、5 分钟详细讲解

如果展开讲，我会先强调一个核心判断：Coding Agent 和普通代码生成的区别，不在于模型是不是能写代码，而在于它是否具备“在环境里持续推进任务”的能力。真实仓库任务往往是这样的：先读项目结构，定位相关文件，再决定跑哪些命令，读到失败信息后继续调整，最后再用测试或 diff 验证结果。这要求系统具备环境观察、工具调用、状态保留和错误恢复能力。

Forge Agent 的核心是一个 ReAct-style coding loop。用户从 `run`、`chat` 或 GitHub Issue 独立入口提交任务后，Agent Core 会先把任务和当前上下文组织成 messages，再调用对应的 LLM backend。模型返回的不是单纯文本，而是尽量转成结构化动作，比如读文件、搜索、跑测试、执行 Shell 或做 Git 操作。动作执行后，工具层会返回 observation，包括成功结果、失败信息或输出摘要，Agent 再把这些 observation 放回下一轮推理里，继续决定后续动作。

为了让这个过程在仓库场景里可用，我把工具层做成了比较明确的仓库工作流能力集合。文件工具负责读取和修改文件，搜索工具负责文本和文件定位，符号能力配合 repo-map 给模型提供更高层的结构信息，Shell 和 Pytest 负责真实命令与测试反馈，Git 工具负责 diff、状态和提交类动作。这样模型不需要“想象仓库里有什么”，而是通过工具逐步探索。

另一个关键问题是上下文。仓库任务很容易出现 prompt 过长的问题，所以不能把整个仓库都塞给模型。我在这里的思路是分层处理：history 保留任务连续性，token budget 控制上下文体积，repo-map 提供轻量级多语言符号摘要，让模型先知道仓库大概结构，再按需读文件。这不是完整语义理解，但在工程上更可控，也更符合现阶段 MVP 的定位。

为了让 Agent 行为可观察、可复盘，我把执行过程写成 JSONL event log。每一轮任务至少会记录 task_start、action、observation、reflection、task_complete 或 task_failed。这样一方面便于调试，另一方面在演示和面试场景里也很有价值，因为可以清楚说明 Agent 是怎么决策的、哪一步失败了、为什么继续调整。基于这些日志，CLI 还提供了 `log list`、`log show` 和 `log replay`，可以从摘要和轨迹两个维度看执行过程。

在模型层面，我没有把主流程和某一家模型厂商绑定，而是做了 Router / Backend 抽象。当前能覆盖 Anthropic、OpenAI、DeepSeek、Groq 和 Ollama。这样主循环和工具系统只关心“拿到什么动作”，而不关心底层具体是哪家模型。对于工程项目来说，这种解耦是必要的，因为 Provider 的接口、能力和可用性都可能变化。

安全边界上，我没有把项目描述成更强的隔离系统，而是保留了更真实的表述。ShellTool 有基础 guardrails，会对明显危险命令做硬拦截，也能在确认模式下识别有副作用的写操作或外部调用。Runtime 层还支持 Docker demo runtime，通过 `--network none`、bind mount、工作目录映射和基础 hardening 参数形成一个 demo-grade execution boundary。它适合演示命令边界，但我不会把它说成更强的安全沙箱。

整体上，这个项目最值得讲的，不是“我做了一个会写代码的 AI”，而是“我把 Coding Agent 的核心工程链路拆清楚、实现出来，并且通过测试和日志把它变成了一个可验证、可解释的系统”。

## 四、项目核心架构讲法

面试时我会按下面这条链路讲：

```text
入口层（CLI / Chat / GitHub Issue 独立入口）
    ↓ Task
Agent Core（ReAct-style coding loop）
    ↓ messages + tools
LLM 层（Backend / Router）
    ↓ Action
工具层（File / Shell / Pytest / Git / Search / Symbol）
    ↓ Observation
上下文层（RepoMap / TokenBudget / History）
    ↓ 日志层（JSONL EventLog / replay）
```

我的讲法会强调三点。

第一，入口层解决的是“任务从哪里来”。`run` 适合一次性任务，`chat` 适合多轮连续交互，GitHub Issue 入口适合更接近真实协作流程的任务来源。

第二，Agent Core 是真正的调度中心。它不是简单透传 prompt，而是把模型输出转成动作，再把动作执行结果变成下一轮推理输入。

第三，日志层不是附属功能，而是工程闭环的一部分。没有日志，Agent 很难解释行为，也很难做复盘和验证。

## 五、核心模块讲解

### 1. ReAct 主循环

- 面试怎么讲：
  我会说这个项目的核心不是某个单点功能，而是 ReAct-style 主循环。它把任务拆成多轮“思考 - 行动 - 观察”，模型每一轮都不是直接结束，而是基于工具返回的 observation 继续决策。
- 面试官可能怎么追问：
  为什么这里写成 ReAct-style，而不是简单说 ReAct？
- 回答要点：
  因为这里强调的是工程上借鉴 ReAct 的循环思想，而不是声称严格复现某一篇论文格式。重点是多轮决策、工具调用和 observation 驱动，而不是术语本身。

### 2. 工具系统

- 面试怎么讲：
  我会说工具系统是 Agent 能落到真实仓库任务上的关键。模型本身不会直接修改仓库，它要通过文件、搜索、Shell、Pytest、Git、符号查找这些工具完成实际操作。
- 面试官可能怎么追问：
  你为什么不只做一个 Shell 工具，其他都交给命令行？
- 回答要点：
  因为仓库任务需要更结构化的 observation。文件读写、搜索、符号查找单独做成工具，更容易给模型稳定输入，也便于做边界控制和测试。

### 3. 多 Provider 路由

- 面试怎么讲：
  我把模型能力收敛到 Router / Backend 抽象，主流程不和单一 Provider 耦合。这样同一套 Agent 逻辑可以切换 Anthropic、OpenAI、DeepSeek、Groq 或 Ollama。
- 面试官可能怎么追问：
  多 Provider 最大的工程价值是什么？
- 回答要点：
  价值在于解耦。主流程不依赖某个厂商 SDK，Provider 差异被收敛在后端层，切换成本更低，也更便于测试 matrix。

### 4. repo-map 上下文摘要

- 面试怎么讲：
  repo-map 解决的是仓库太大、上下文太长的问题。它不是把代码完整读进去，而是先给模型一个结构化、多语言的符号级摘要。
- 面试官可能怎么追问：
  这和完整语义理解有什么区别？
- 回答要点：
  repo-map 是轻量级结构摘要，不是完整语义模型。它的目标是帮助模型快速定位可能相关的模块，而不是替代后续按需读文件。

### 5. JSONL event log

- 面试怎么讲：
  我会强调 event log 是可观察性的核心。没有日志，Agent 只剩最终输出，很难解释中间过程；有了 JSONL event log，就能看到每一轮 action、observation、reflection 和最终状态。
- 面试官可能怎么追问：
  replay 的意义是什么？
- 回答要点：
  replay 不是确定性重执行，而是执行轨迹复盘。它帮助调试、审计和演示，让 Agent 的行为从黑盒变成可以逐步讲清楚的过程。

### 6. Shell guardrails

- 面试怎么讲：
  Shell 工具是能力最强、风险也最高的一层，所以我做了基础 guardrails，包括危险命令硬拦截和确认模式下的副作用识别。
- 面试官可能怎么追问：
  这是不是安全沙箱？
- 回答要点：
  不是。它是基础风险控制，目标是提升工程可控性，不是把项目包装成更强隔离系统。

### 7. Docker demo runtime

- 面试怎么讲：
  Runtime 抽象把“命令做什么”和“命令在哪里执行”分开。Docker runtime 用来提供 demo-grade execution boundary，比如断网、挂载仓库、约束工作目录和基础资源参数。
- 面试官可能怎么追问：
  为什么要单独做 Runtime 层？
- 回答要点：
  因为 Shell、Pytest、Git 不应该各自决定执行环境。把运行边界抽到 Runtime 层，工具层更简单，边界也更一致。

### 8. GitHub Issue-to-patch flow

- 面试怎么讲：
  这个入口是把 Agent 放到更接近实际协作场景里。任务不是直接从命令行输入，而是来自 Issue 描述，后续再衔接本地修复、commit 和 PR 演示流程。
- 面试官可能怎么追问：
  这是单独实现了一套 Agent 吗？
- 回答要点：
  不是。它复用的是已有 Agent 核心链路，只是换了任务来源和外层包装方式。

## 六、技术难点与解决方案

### 1. LLM 如何稳定调用工具

难点在于模型天然更擅长生成文本，不一定稳定输出可执行动作。我的处理方式是把工具动作结构化，优先走明确的工具调用协议；在缺少原生能力时，再用 JSON fallback 保持动作语义稳定。

### 2. 上下文窗口不够怎么办

不能把整个仓库都塞进 prompt。我的做法是用 repo-map 提供结构摘要，用 history 保留任务连续性，用 token budget 限制上下文体积，真正的文件内容按需读取。

### 3. 工具失败后如何恢复

关键不是“避免失败”，而是“把失败变成可用 observation”。只要工具返回足够结构化的错误信息，Agent 就能继续判断是重试、换路径、补文件还是终止任务。

### 4. 如何避免 Agent 死循环

主要依赖主循环的步数上限、状态判断和结束分支。也就是说，Agent 不是无限跑下去，而是在达到 `finish`、`give_up`、失败边界或最大步数后明确结束。

### 5. 如何记录和复盘 Agent 行为

我用 JSONL event log 把执行过程拆成事件流，再通过 summarize 和 replay 做摘要和轨迹回放。这样不只是“知道结果”，而是知道过程。

### 6. 如何处理不同模型 Provider 的差异

差异主要体现在 SDK、协议和能力暴露方式上。我的处理方式是把差异收敛到 Router / Backend 层，上层 Agent 不感知具体厂商，只面向统一接口。

### 7. 如何约束 Shell 命令风险

我没有试图一次性做更强隔离，而是先做基础可验证 guardrails：危险命令直接拦截，明显副作用命令要求确认；如果需要更明确的执行边界，再通过 Docker runtime 补一层 demo-grade 约束。

## 七、面试高频追问与回答

### 1. 你这个和普通 ChatGPT 生成代码有什么区别？

普通代码生成通常停留在一次性回答，而这个项目解决的是仓库任务闭环。它会观察环境、调工具、跑测试、看失败、继续修复，并记录整个执行过程。

### 2. 为什么用 ReAct-style 而不是直接说 ReAct？

因为我想强调的是工程实现上的“ReAct 风格循环”，不是声称严格复现某个学术框架。重点是多轮决策、动作执行和 observation 驱动。

### 3. function calling 和 JSON fallback 有什么区别？

function calling 是原生结构化工具调用，协议更稳；JSON fallback 是没有原生接口时的兼容方案，本质上都是把模型输出转成可执行动作。

### 4. repo-map 为什么有必要？

因为仓库任务最大的瓶颈之一是上下文长度。repo-map 先给模型一个结构化摘要，让它知道该去哪里读文件，而不是一上来就把整个仓库展开。

### 5. 你的 Agent 如何知道该读哪个文件？

一方面来自任务描述和已有 history，另一方面来自搜索、repo-map 和符号信息。模型先通过这些轻量信息做判断，再决定是否进一步读取具体文件。

### 6. 工具执行失败怎么办？

失败不会直接让系统失控，而是被包装成 observation 返回给 Agent。模型可以基于错误结果继续调整动作，或者在必要时结束任务。

### 7. 如何避免无限循环？

通过最大步数、明确结束状态和失败退出分支来控制。也就是说，它是可终止的调度循环，不是无限制自动运行。

### 8. event log 有什么价值？

它的价值在于可观察性和可复盘。没有日志时你只能看到最终结果，有日志时你能解释 Agent 的中间行为，也更容易做调试和演示。

### 9. Docker runtime 是不是安全沙箱？

不是。它是 demo-grade execution boundary，适合做演示和边界控制说明，但我不会把它讲成更强隔离系统。

### 10. 多 Provider 路由怎么设计？

先定义统一 backend 接口，再用 Router 根据 provider / model 配置选择后端实现。这样 Agent Core 只依赖统一抽象，不依赖具体厂商。

### 11. 这个项目最大的难点是什么？

我认为最大的难点不是单个模块，而是把模型推理、工具执行、上下文控制、失败恢复和日志复盘真正串成一条工程链路，并保证每一段都能验证。

### 12. 如果继续优化，你会做什么？

我会先从上下文压缩、工具选择策略、日志可视化和更细粒度的权限控制继续往下做。但在当前阶段，我更强调的是核心链路已经跑通并且可验证，而不是盲目扩展功能。

## 八、项目边界怎么说

如果面试官问项目边界，我会这样回答：

这个项目的定位是工程化 MVP，不是更重的产品系统。我重点解决的是 Coding Agent 的核心工程链路，也就是任务进入、ReAct-style 决策、工具执行、上下文控制、测试反馈和执行轨迹复盘。Docker runtime 的定位是 demo-grade execution boundary，不是更强隔离环境；repo-map 是符号级摘要，不是完整语义理解；event replay 是轨迹回放，不是确定性重执行。这个项目也没有声称任何 SWE-bench 成绩。它最核心的价值是把 Coding Agent 的关键能力做成了一个可运行、可验证、可讲清楚的工程系统。
